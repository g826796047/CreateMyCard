# Python 编码与 CodeCheck 规范

本文适用于项目内 Python 源码、测试、生成器和脚本。修改代码时按“业务语义正确、类型与异常语义稳定、
清晰可维护、满足静态检查”的顺序处理；CodeCheck 整改只能调整代码组织，不得改变接口、数据模型或业务语义。

本文是各开发会话和工作区共用的 CodeCheck 规范入口。新增告警经验统一补充到本文，不只保存在会话
记忆、本地报告或屏蔽记录中，也不另建相互重复的清单。开始修改及提交前都应复读本文；旧检出还需
核对最新 main 中的 CodeCheck 规则，保留其他会话已补充的规则，不覆盖或擅自改动其工作区。

禁止为了消除告警而：

- 用 `""`、`0`、空容器或其它伪值替代 `None`，或把数字、布尔值、列表、字典强制转成字符串。
- 修改原有返回类型、异常行为、顺序或去重语义。
- 将必选字典键改成未检查的 `get()` 后继续使用。
- 通过字符串拼接、格式化或拆分规避公网地址、敏感信息等扫描规则。
- 直接修改自动生成文件而不修复生成器、源模板或其它生成源。

## 格式与控制流

- 只使用 4 个空格缩进，禁止 Tab、混合缩进和无意义的额外缩进；调整缩进前先确认代码块层级，不能机械
  改写导致语义变化。
- 模块级函数和类之间保留两个空行；类成员、嵌套函数和装饰器方法之间保留合理的一个空行。
  `expected 2 blank lines, found 0` 表示定义之间缺少空行，只补齐分隔，不改变函数体或调用顺序。
  合并冲突后须复核函数边界；`semantic/layout/geometry.py` 的标题高度预算辅助函数按此修复，
  使用 Ruff 的 `--preview --select E302,E305` 专项检查，相关行为回归见
  `tests/l0/integration/test_s_center_numeric_focus.py`。
- 一行只写一条语句，函数体不得与 `def` 或 `async def` 写在同一行。
- 单行代码不得超过 120 个字符；`widget_service/` 内 Python 代码还必须遵守 Ruff 的 100 字符行宽限制。
  长调用、长签名和长字符串应在保持内容等价的前提下主动换行。
- 遵守 `G.FMT.04`，slice 的冒号前不得有空格。已确认字符串具有目标前缀时优先使用
  `removeprefix()`，不要使用会被格式化为 `value[index :]` 的计算切片。
- formatter 与 lint 规则冲突时，统一修正项目配置，避免在两套格式之间反复改写源码。
- 遵守 `G.CTL.03`，`if`、`elif`、`while` 等条件控制语句最多包含 3 个布尔表达式；嵌套括号和
  换行不会减少条件数量。超过时优先按职责拆为类型检查、值检查等保护分支，或使用有语义的中间变量、
  状态对象或独立辅助方法。保持原短路顺序和异常类型/信息，不能在类型检查前对不合法类型做成员访问。
  `single_step_edit.py` 的静态文字检查采用“原值类型检查 + 动态绑定检查”，并以
  `test_single_step_edit.py` 的条件数量与行为回归防止再次引入同类告警；已屏蔽不代表无需源码整改。
- 清晰显式优先于紧凑写法；筛选逻辑优先使用早期 `continue`，避免深层嵌套。

## 推导式、字典访问与返回值

- 推导式只用于一层 `for` 和最多一个简单 `if`。出现多个 `for`、多个 `if`、跨行复杂条件、赋值表达式
  `:=`、复杂调用与判断组合，或同时承担排序、去重、状态更新时，必须展开为显式循环；测试代码同样适用。
- 遵守 `G.EXP.04`，每个 `for ... in ...`、`if ...` 子句必须完整写在同一行；即使只有一个简单
  `for`，把 `in` 后的元组换到下一行也会告警。固定少量 schema 字段优先写显式字典，动态字段用显式循环，
  不以跨行推导式规避行宽。2026-10-17 的主题注册表 frame 字段和 ballColors 字段均按此整改；
  `test_theme_codecheck_regressions.py` 检查注册表的推导式子句及 schema 等价性。
  2026-11-23 组件配方测试的排除集合导致推导式 `if` 子句跨行，改为独立集合与显式循环，
  保持筛选范围、字典顺序及配方对象引用不变；回归见
  `tests/l0/unit/test_compact_component_runtime.py::test_visual_recipe_contract_uses_consistent_icon_and_overflow_rules`。
- 展开 `dict.fromkeys(generator)` 等代码时必须保留原有顺序和去重语义；不能直接改成无序 `set`。
- 除非当前作用域已显式证明键存在，否则不得直接使用 `mapping[key]`。可选键使用 `get()` 并检查结果；
  必选键使用 `get()` 后显式 `raise`，测试中使用 `get()` 后显式 `assert`。
- 当 `None` 是字典的合法值时，使用独立 sentinel 区分“键不存在”和“值为 `None`”。
- 遵守 `G.CTL.01`。返回 `Optional`、`Union` 或 `Any` 的函数存在不同类型的多个分支时，优先赋值给带
  类型标注的局部变量并在末尾统一返回，同时保持真实类型和 `None` 语义。
  元组元素可空时同样适用：`(None, None)` 与 `(dict, str)` 分支使用带完整元组类型的局部变量统一返回，
  不以空字典或空字符串代替未匹配。`photo_facts._main_scope` 保留主区对象身份、方向与歧义拒绝语义，
  由 `test_theme_codecheck_regressions.py` 检查单一返回出口和各分支的两元素返回约定。
- 遵守 `G.FNM.05`。函数需要返回较多数据时，使用数据类、具名元组等具名结构，避免难以辨认的位置解包。

## 类型、异常、生成代码与扫描误报

- 遵守 `G.TES.01`。生产业务代码禁止使用 `assert` 语句，不能依赖可能在 `python -O` / `-OO`
  优化模式下被删除的检查。业务不变量使用显式条件检查及异常，整改保留原异常类型、处理路径与业务语义；
  测试代码仍可使用 `assert`。2026-11-03 的每日计次路由按此整改，
  `test_daily_usage_routes.py` 检查生产入口不存在断言语句，并覆盖普通及优化编译下的空值检查和成功计次。
- 遵守 `G.VAR.01`。带类型标注的变量和数据类字段使用同类型初始值，例如 `float` 字段使用 `0.0`，
  避免生命周期内由 `int` 隐式变为 `float`。
- 遵守 `G.VAR.03`。局部变量和参数不得遮蔽外部作用域的标识符，包括导入的 `field`、`role`；
  改用 `schema_field`、`color_role` 等准确命名。
  函数内延迟导入同样不得重复绑定模块级已导入的名称；已有可用模块导入时直接复用。
  2026-11-20 转换器重复导入 `VISUAL_RECIPE_VERSION` 按此等价移除，
  `test_theme_codecheck_regressions.py` 检查转换器局部导入不遮蔽模块级导入。
  2026-11-22 图案创建回归的嵌套保存回调参数改为 `saved_artifact`，避免遮蔽外层产物变量；
  参数改名须保持回调传参与对象身份不变。`tests/l0/unit/test_compact_codecheck_regressions.py`
  覆盖图案编译模块及创建回调的词法作用域，区分真实外层绑定与类成员作用域。
- 遵守 `G.ERR.09`。同一个 `except` 元组不得同时捕获父异常和子异常；例如已捕获 `OSError` 时，不再
  重复列出其子类 `TimeoutError`。
- 遵守 `G.ERR.07`。不得使用 `except` 后直接 `pass`；可选流程发生异常时也要记录异常类型和原因，
  必要时转换为明确的业务失败。
- 生成文件出现问题时先修复 generator、source prompt、template 或 build script，再重新生成。确属不可改的
  生成产物时，才按项目统一配置处理检查范围，不在单个文件中随意屏蔽规则。
- 四段数字版本号等真实协议值被公网地址扫描误报时，必须保留协议语义，并使用项目批准的白名单或抑制
  机制；不得改写真实值规避扫描。`noqa`、规则屏蔽和豁免不能替代可读的源码修复，只能用于已确认且无法
  通过等价代码修复的误报。
- 从 Skill 批量同步 `widget_service/cloud/services/card_validation/` 后，不得直接以覆盖后的源码作为最终
  结果。必须重新执行 CodeCheck，并恢复微服务侧为满足本文规则所做的等价改写。
- 当前校验器重点复查：`binding_validator.py` 的前缀截取、`component_validator.py` 的模板变量判断、
  `protocol_validator.py` 的入口状态判断，以及 `source_parser.py` 的表达式标记判断。

## 修改后验证

修改 Python 代码后至少执行 Ruff、相关单元测试和差异空白检查，并复核：缩进与空行、单行长度、复杂
推导式、未保护字典访问、多类型返回、异常处理、生成源，以及顺序、去重、返回类型和业务语义是否保持不变。

提交前必须对本次改动逐项检查上述规则，新增可复现告警应补充相应回归测试。Ruff 通过不能替代企业
CodeCheck；本地没有企业扫描器时，明确报告已做的专项检查和未执行的企业检查，不声称全部 CodeCheck
通过。跨会话提交统一引用本文，新经验注明规则编号、等价修复原则及对应回归位置。
